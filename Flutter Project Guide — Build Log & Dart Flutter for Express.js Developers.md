## Part 1 — What we have built so far

`my_first_app` is now a working **login / sign-up app** called "Construction-Site Demo". It replaced Flutter's default counter template with three screens' worth of code, a user model, a fake auth service and two automated tests.

What works today:

- **Auth screen** with two modes — *Log in* and *Sign up* — toggled by a text button.
- **Form validation**: name, email format, password length (6+ on sign-up), confirm-password match, role.
- **Loading state**: the button shows a spinner while the fake 600 ms "network call" runs.
- **Error messages** from the service ("Incorrect email or password.", "An account with this email already exists.").
- **Home screen** that greets the user by name, shows their email, and has a log-out button.
- **Widget tests** that sign up end-to-end and check empty-form validation.

What it does **not** do yet: accounts live only in memory, so they disappear when the app restarts. There is no real backend (Express API, Firebase, etc.) yet — `AuthService` is the single place to swap that in later.

| `lib/screens/auth_screen.dart` | The form UI, validation, loading/error state, navigation to Home | A route handler + the HTML/EJS view it renders |

The flow between them: `main.dart` → `AuthScreen` → calls `AuthService` → gets back a `UserModel` → navigates to `HomeScreen(user)` → logout returns to `AuthScreen`.

## Part 2 — Understanding Dart & Flutter through Express.js

The biggest shift first: **Express runs on the server and answers requests; Flutter runs on the user's device and draws the screen.** In a real app they work together — Flutter is the client that calls your Express API. Everything below maps what we wrote to the Express idea you already know.

### Step 1 — Dart is "typed JavaScript"

Dart looks like JS/TypeScript, with types checked before the app runs.

```javascript
// JavaScript
const name = 'Ada';
let count = 0;
let nickname = null;
```

```dart
// Dart
final String name = 'Ada';   // final = set once (like const in JS)
int count = 0;               // can change (like let)
String? nickname;            // ? = may be null (null safety)
```

- `final` = assigned once at runtime. `const` = known at compile time (e.g. `const SizedBox(height: 16)`), which lets Flutter reuse it.
- **Null safety**: `String` can never be null; `String?` can. That is why `_error` is `String?` and we write `_error!` ("I promise it's not null") when showing it.
- `??` works like JS: `value?.trim() ?? ''` in `_validateEmail`.
- String interpolation: `'Hello, ${user.name}!'` = JS template literal `` `Hello, ${user.name}!` ``.

### Step 2 — Entry point: `main()` vs `app.listen()`

```javascript
// Express: server.js
const app = express();
app.get('/', (req, res) => res.render('login'));
app.listen(3000);
```

```dart
// Flutter: main.dart
void main() {
  runApp(const MyApp());            // start the app
}

class MyApp extends StatelessWidget {
  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      title: 'Construction-Site Demo',
      home: const AuthScreen(),      // first "page", like the '/' route
    );
  }
}
```

`main()` is the one function Dart always runs first, like `node server.js`. `MaterialApp` is like the `app` object: global config (title, theme) plus the first screen.

### Step 3 — Classes, constructors and named parameters (the Model)

```javascript
// Express / Mongoose
const UserSchema = new Schema({
  name:  { type: String, required: true },
  email: { type: String, required: true },
  role:  { type: String, default: 'user' },
});
```

```dart
// lib/models/user_model.dart
class UserModel {
  const UserModel({
    required this.name,      // must be passed
    required this.email,
    this.role = 'user',      // default value
  });

  final String name;
  final String email;
  final String role;
}

// usage — named arguments, like passing an options object in JS
UserModel(name: 'Ada', email: 'ada@example.com');
```

- `{ ... }` in a constructor = **named parameters**, like `function f({ name, email })` in JS.
- `this.name` in the parameter list assigns the field automatically — no `this.name = name` line needed.
- Unlike Mongoose, this model does not talk to a database; it is just a typed data shape.

### Step 4 — Services and singletons

In Node, `module.exports = new AuthService()` gives every `require()` the same instance because modules are cached. Dart does it explicitly:

```dart
class AuthService {
  AuthService._();                                   // private constructor
  static final AuthService instance = AuthService._(); // the one shared instance

  final Map<String, ({UserModel user, String password})> _accounts = {};
}

// usage anywhere
AuthService.instance.login(email: e, password: p);
```

- An **underscore** prefix (`_accounts`, `AuthService._`) means **private to this file**. Dart has no `private` keyword.
- `({UserModel user, String password})` is a **record** — a quick typed object, like `{ user, password }` in JS.
- `_accounts` is our stand-in for a database table. In Express you would query MongoDB/Postgres here instead.

### Step 5 — `Future` + `async`/`await` = `Promise` + `async`/`await`

```javascript
// Express service
async function login(email, password) {
  await new Promise(r => setTimeout(r, 600));
  const user = await User.findOne({ email });
  if (!user || user.password !== password) throw new AuthError('Incorrect email or password.');
  return user;
}
```

```dart
// lib/services/auth_service.dart
Future<UserModel> login({required String email, required String password}) async {
  await Future.delayed(const Duration(milliseconds: 600)); // fake network delay
  final account = _accounts[email.trim().toLowerCase()];
  if (account == null || account.password != password) {
    throw const AuthException('Incorrect email or password.');
  }
  return account.user;
}
```

`Future<UserModel>` = "a Promise that resolves to a UserModel". The keywords work the same way.

### Step 6 — Errors: custom exceptions and `try / on / catch / finally`

```javascript
// Express
class AuthError extends Error {}
try { const user = await login(e, p); res.redirect('/home'); }
catch (err) { if (err instanceof AuthError) res.render('login', { error: err.message }); }
finally { /* cleanup */ }
```

```dart
// auth_screen.dart — _submit()
try {
  final user = await auth.login(email: ..., password: ...);
  Navigator.of(context).pushReplacement(...);   // like res.redirect('/home')
} on AuthException catch (e) {                  // catch only this type
  setState(() => _error = e.message);           // like res.render('login', { error })
} finally {
  if (mounted) setState(() => _isLoading = false);
}
```

`on AuthException catch (e)` is Dart's built-in version of `if (err instanceof AuthError)`.

### Step 7 — Everything is a Widget (the "view" layer)

In Express you render HTML with a template (EJS/Pug) or send JSON. In Flutter you **return a tree of widgets** from a `build()` method. Each widget is a Dart object; nesting them builds the screen.

```html
<!-- EJS-ish -->
<div class="center">
  <div class="column">
    <h2>Hello, <%= user.name %>!</h2>
    <p><%= user.email %></p>
  </div>
</div>
```

```dart
// home_screen.dart
Center(
  child: Column(
    mainAxisSize: MainAxisSize.min,
    children: [
      Text('Hello, ${user.name}!', style: Theme.of(context).textTheme.headlineMedium),
      const SizedBox(height: 8),   // spacing, like margin-top: 8px
      Text(user.email),
    ],
  ),
)
```

Widgets we used and their HTML/CSS cousins:

| Widget | Rough HTML/CSS equivalent |
| --- | --- |
| `Scaffold` | Page layout: `<header>` + `<main>` |
| `AppBar` | `<header>` / navbar |
| `Center` | `display:flex; justify-content:center; align-items:center` |
| `Column` / `Row` | `flex-direction: column` / `row` |
| `SizedBox(height: 16)` | A 16px spacer / margin |
| `SingleChildScrollView` | `overflow: auto` |
| `ConstrainedBox(maxWidth: 420)` | `max-width: 420px` |
| `SafeArea` | Padding that avoids the phone notch |
| `Text` | `<p>` / `<span>` |
| `TextFormField` | `<input>` with validation |
| `FilledButton` / `TextButton` / `IconButton` | `<button>` styles |
| `Wrap` | `flex-wrap: wrap` |
| `ThemeData` / `Theme.of(context)` | A global CSS file / CSS variables |

### Step 8 — `StatelessWidget` vs `StatefulWidget` (the most important idea)

Express is stateless per request: every request builds a fresh response, and anything you need to remember goes in a DB or session. A Flutter screen **stays alive** and re-draws when its data changes.

- **`StatelessWidget`** (`HomeScreen`, `MyApp`): only shows what it was given. Like a template rendered with fixed `res.locals`.
- **`StatefulWidget`** (`AuthScreen`): holds data that changes while you look at it — `_isLogin`, `_isLoading`, `_error`. It is split in two classes:

```dart
class AuthScreen extends StatefulWidget {            // the config (immutable)
  @override
  State<AuthScreen> createState() => _AuthScreenState();
}

class _AuthScreenState extends State<AuthScreen> {   // the living state
  bool _isLogin = true;

  void _toggleMode() {
    setState(() {            // "data changed — please re-run build()"
      _isLogin = !_isLogin;
    });
  }

  @override
  Widget build(BuildContext context) { ... }  // re-runs after every setState
}
```

`setState()` is the key: change a variable inside it and Flutter re-runs `build()` and updates the screen. In Express terms it is like calling `res.render()` again automatically every time the data changes — without a new request. Change a variable **without** `setState` and nothing on screen updates.

### Step 9 — Conditional UI: collection `if` and spread `...`

One screen serves both modes by adding fields only in sign-up mode — like `<% if (!isLogin) { %>` in EJS or `{!isLogin && <input/>}` in JSX.

```dart
children: [
  if (!_isLogin) ...[            // only in sign-up mode
    TextFormField(controller: _nameController, ...),
    const SizedBox(height: 16),
  ],
  TextFormField(controller: _emailController, ...), // always shown
]
```

`...[a, b]` spreads a list into the parent list, exactly like JS `...[a, b]`.

### Step 10 — Forms, controllers and validation

| Express | Our Flutter code |
| --- | --- |
| `req.body.email` | `_emailController.text` |
| `express-validator`: `body('email').isEmail()` | `validator: _validateEmail` on the `TextFormField` |
| `validationResult(req).isEmpty()` | `_formKey.currentState!.validate()` |
| Send errors back in the response | Validator returns a `String` → shown under the field; returns `null` → valid |

```dart
String? _validateEmail(String? value) {
  final email = value?.trim() ?? '';
  if (email.isEmpty) return 'Enter your email';                  // error text
  if (!RegExp(r'^[^@\s]+@[^@\s]+\.[^@\s]+$').hasMatch(email)) return 'Enter a valid email';
  return null;                                                     // valid
}
```

- A `TextEditingController` holds the text of one input. We create 5 of them.
- `GlobalKey<FormState>` is a handle to the `Form` so we can call `validate()` and `reset()` on all fields at once.
- `dispose()` frees the controllers when the screen is destroyed — like closing a DB connection or clearing an interval in Node to avoid leaks.
- Always validate on the server too: when this talks to Express later, the Express validation is the one you trust.

### Step 11 — Navigation = routing / redirects

```javascript
// Express
res.redirect('/home');                 // after login
req.session.user = user;               // pass data to the next page
```

```dart
// Flutter
Navigator.of(context).pushReplacement(
  MaterialPageRoute(builder: (_) => HomeScreen(user: user)), // data passed in the constructor
);
```

- The `Navigator` keeps a **stack** of screens. `push` adds one (the back button returns); `pushReplacement` swaps the current one so Back cannot return to the login form — the right choice after login and logout.
- Data is passed as a constructor argument (`HomeScreen(user: user)`), not via a session.
- `if (!mounted) return;` checks the screen still exists after the `await` — similar to checking `res.headersSent` before responding.

### Step 12 — Tests: widget tests vs Supertest

```javascript
// Jest + Supertest
const res = await request(app).post('/signup').send({ name: 'Ada', ... });
expect(res.text).toContain('Hello, Ada!');
```

```dart
// test/widget_test.dart
await tester.pumpWidget(const MyApp());                       // start app
await tester.tap(find.widgetWithText(TextButton, 'Sign up'));  // click
await tester.enterText(find.widgetWithText(TextFormField, 'Email'), 'ada@example.com');
await tester.tap(find.widgetWithText(FilledButton, 'Sign up'));
await tester.pumpAndSettle();                                  // wait for the 600 ms + animations
expect(find.text('Hello, Ada!'), findsOneWidget);
```

`pump()` draws one frame; `pumpAndSettle()` keeps drawing until nothing is moving — like awaiting the response in Supertest.

### Step 13 — Next: connecting Flutter to an Express API

This is where your Express skills plug in. Only `AuthService` changes; the screens stay the same.

```javascript
// Express: routes/auth.js
router.post('/login', async (req, res) => {
  const user = await User.findOne({ email: req.body.email });
  if (!user || !(await bcrypt.compare(req.body.password, user.password))) {
    return res.status(401).json({ message: 'Incorrect email or password.' });
  }
  res.json({ token: signJwt(user), user: { name: user.name, email: user.email, role: user.role } });
});
```

```dart
// Flutter: AuthService.login using package:http (flutter pub add http)
Future<UserModel> login({required String email, required String password}) async {
  final res = await http.post(
    Uri.parse('http://10.0.2.2:3000/api/auth/login'), // 10.0.2.2 = your PC from the Android emulator
    headers: {'Content-Type': 'application/json'},
    body: jsonEncode({'email': email, 'password': password}),
  );
  final data = jsonDecode(res.body);
  if (res.statusCode != 200) throw AuthException(data['message']);
  return UserModel(name: data['user']['name'], email: data['user']['email'], role: data['user']['role']);
}
```
